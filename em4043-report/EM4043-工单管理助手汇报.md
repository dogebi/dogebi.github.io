# 把分散的工单信息，变成可执行的管理判断

围绕 T1、T2、现场管理、SM 四类用户，展示工单管理助手如何从查询、分析、统计延伸到客户月报。

## 一、设计理念

实测数据已经说明，工单助手的核心价值在于统一信息口径，并把信息整理成下一步行动。

> 工单管理助手不是简单替代人工查询，而是把工单、知识库、历史经验和人员记忆，统一转换为可执行的分析结果。

### 当前能证明的能力

能够快速回答总量、类型、处理时长、长期未解决事项等问题，并生成面向不同角色的结构化结果。

- 以 Agent 为主：理解项目、工单和技术上下文，能够查监控、进行对话，并与人共同完成工单。
- 自动整理数据：识别不同格式的资料，自动归类并沉淀到知识库，减少人工整理成本。

| 指标 | 数值 |
| --- | ---: |
| 项目工单总数 | 15 |
| 已关闭或已完成 | 9 |
| 完成率 | 60% |
| 处理中或未完结 | 6 |
| 变更相关工单 | 10 |
| 未完结累计占用时长 | 93 小时 |

## 二、设计目标（对比）

从固定流程与人工整理，转向以 Agent 为主、可理解上下文并持续沉淀知识的工单协作方式。

| 传统方式 | 工单管理助手目标 |
| --- | --- |
| 按固定流程执行，遇到复杂问题需要人工判断。 | 以 Agent 为主，理解项目、工单和技术上下文，与人对话并共同完成工单。 |
| 人工跨系统查找、整理和确认数据。 | 自动识别不同格式的数据，整理、归类并沉淀到知识库。 |
| 结果依赖个人经验，难以持续复用。 | 结合工单、资产、历史案例、知识库和监控信息，输出可验证的分析结果。 |

### 知识库数据流摘要

- **接入与任务：**Web、第三方 API 或 MCP 通过 FastAPI 接入；上传接口立即返回 `task_id`，由后台任务异步处理。
- **解析与切片：**根据文件格式进行 Markdown、PDF、Excel、OCR 等解析和清洗，再按 `standard`、`manufacturing`、`code` 等场景策略切片。
- **基础入库：**切片生成 Embedding 后写入原始 Qdrant Collection，同时建立 BM25 关键词索引；文件、切片追踪和状态写入 MySQL，原始与 Markdown 文件保存在文件系统。
- **元数据增强：**LLM 为切片生成 `questions`、`keywords`、`tags`、`summary`。小规模切片可立即处理，中等规模进入 Redis 队列由独立 Worker 异步处理，大规模任务进入待处理状态。
- **智能检索：**`smart_search` 根据增强开关选择标准 HybridRetriever 或 MultiVectorRetriever；原始内容与增强元数据分别进行向量检索和 BM25 检索，再按 `slice_id` 融合。
- **排序与输出：**融合结果经过阈值过滤、Reranker 和可选的 LLM Refine，返回最终 Top-K；PDF 还可通过独立的 PageIndex 树进行章节级推理检索。
- **存储与协同：**Qdrant 保存原始/增强向量，MySQL 保存业务元数据和增强记录，Redis 管理任务队列与缓存，文件系统保存 Markdown、BM25 索引和 PageIndex 树。

**核心价值：**非结构化资料经过“解析—切片—向量化—关键词索引—元数据增强”形成可持续迭代的知识资产；Agent 可根据问题类型选择语义、关键词、增强元数据或章节结构进行检索。

## 四、业务场景：四类用户，四种结果

同一批工单数据，按照不同角色的工作目标重新组织，直接服务于客户沟通、技术处理和管理决策。

### 业务场景1：客户问题快速定位与反馈（T1）

关注是否及时受理、当前进展、预计方向和最终客户反馈。

**传统人工方式：**

- 在 Jira、历史文档、聊天记录和经验库之间反复查找。
- 人工确认状态、负责人和处理进展。
- 手工整理问题描述、处理过程和客户回复。
- 交接班容易遗漏待办事项和风险信息。

**工单助手输出：**

- 问题概述与当前影响范围。
- 已完成动作、负责人和工单状态。
- 下一步处理建议和客户可读说明。
- 交接待办与风险提示。
- 导入 KB（知识库）内容，辅助问题定位。

**核心收益：**T1 可以从“逐单查找和确认”转为“按优先级处理和跟进”，缩短工单整理时间，并加快首次故障报告生成。

### 业务场景2：技术问题分析与解决方案生成（T2）

关注根因分析、影响范围、历史相似问题和可执行的处理方案。

- **传统人工方式：**手动检索历史工单、知识库和变更记录，依靠个人经验判断根因，人工比对设备、资产和近期变更，并单独编写排查、回滚和验证方案。
- **工单助手输出：**区分事实与推测，关联历史案例、近期变更和影响范围，生成排查步骤、处理方案、回滚方案和变更后验证项目，并通过 SOP 蒸馏沉淀可复用流程。
- **EM4043 实测依据：**变更相关工单共有 10 张，占总工单数 66.7%。EM4043-2、3、8、9 适合联合分析处理进度与技术风险。

### 业务场景3：工单统计、人员负载和异常管理（现场管理）

关注全局运行情况、状态分布、负责人、处理时长和异常事项。

- **传统人工方式：**找负责人询问状态、导出 Jira 制作统计表，并人工识别超时和长期未关闭工单。
- **工单助手输出：**直接回答总数、类型、未关闭工单和负责人，筛选处理时间超过 3 小时的工单，识别长期停滞事项和管理介入点。
- **EM4043 实测依据：**处理时间超过 3 小时的工单有 6 张，超过 21 小时仍未解决的工单有 3 张，未完结工单累计占用时长约 93 小时。EM4043-2、3、8 是重点关注事项。

### 业务场景4：客户月报、项目统计和管理分析（SM）

关注客户月报、项目趋势、服务质量、工单分类和资源投入情况。

- **传统人工方式：**从 Jira 导出数据，再找 T1、T2 和负责人补充情况，手工整理月度统计，制作 Word、Excel 和 PPT 并反复确认口径。
- **工单助手输出：**按项目和周期生成工单总量及类型分布，输出完成率、平均处理时长和超时工单，提炼风险和管理结论，并生成管理版与客户可读的月报初稿。
- **EM4043 实测依据：**已关闭或完成工单平均处理时长约 6 小时 37 分钟，未完结工单累计占用时长约 93 小时，目前有 3 张超过 21 小时仍未解决的工单。

## 五、四类用户的价值变化

价值不在于把每一步都自动化，而在于让每个角色更快得到适合自己工作的结果。

| 用户 | 主要关注点 | 传统方式 | 工单助手带来的变化 |
| --- | --- | --- | --- |
| T1 | 快速定位、客户反馈、交接完整 | 查资料、问负责人、手工写回复 | 自动汇总工单情况并生成客户说明 |
| T2 | 根因分析、风险判断、解决方案 | 依赖经验，手动查文档和历史工单 | 综合分析工单、变更、知识库并生成排查方案 |
| 现场管理 | 总量、状态、负责人、超时和风险 | 手工统计、找人确认 | 自动生成全局统计并发现异常 |
| SM | 月报、客户汇报、趋势分析 | 导出数据并手工制作文档 | 自动生成统计结果、管理结论和报告初稿 |

## 六、当前进展

通过真实业务场景持续验证 AI 的使用价值，并同步完成问题闭环和输出质量优化。

- **主动交互：**让大家主动与 AI 交互，在实际工单处理中找到有价值、可复用的应用场景。
- **问题对应：**持续收集、定位和跟进使用过程中发现的问题，推动 Bug 对应和闭环处理。
- **提示词调整：**调整提示词和回答约束，避免出现有逻辑的胡说八道以及编造数据。

## 七、面临的主要课题

- **知识库：**工单、资产知识库的完整性与持续优化，以及查询机制的进一步完善。
- **复杂查询：**Agent 调用 MCP 时偶尔生成过于复杂的查询，导致执行时间过长甚至卡死。
- **系统稳定性：**持续排查系统资源或业务逻辑问题导致的故障，完善监控、定位和恢复机制。

## 八、未来扩展（畅想）

- **Skill 能力扩展：**增加爬虫、源码抓取和官方文档采集能力，进行更深入的技术分析，提高回答准确性。
- **引擎替换与增强：**探索使用 DeepSeek Harness 等方案替换或增强当前引擎，让 AI 获得更强的理解、规划和执行能力。
