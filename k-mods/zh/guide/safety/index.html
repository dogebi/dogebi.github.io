如何安全使用 mod

mod 在没有沙箱的情况下、以我的权限运行在 Claude Code 内。所以在安装之前了解它能做什么很重要。本文整理 mod 能触及的范围、安装前自行确认的方法、k-mods 的审查标准与权限标签、组织管理员可用的管控，以及需要警惕的信号。

mod 没有沙箱

mod 一旦加载，就能做这些事。

  • 在我的电脑上以我的身份行动：在我的账号能碰到的任何地方读写文件、运行程序、发网络请求。
  • 读取我的机密信息：读环境变量和设置文件。里面的 API key 也算。
  • 查看我的会话：看我发的所有提示和 Claude 调用的所有工具。
  • 改动我的会话：可以改写提示或工具调用、冒充我发提示，或给我其他会话发消息。
  • 不问即行动：可以在问用户之前就批准工具调用。
  • 消耗我的用量：用我的套餐或 API key 调模型。

沙盒即使开启了，mod 也不受影响。沙箱只隔离 Claude 执行的 Bash 命令，mod 自行启动的进程在沙箱之外运行。

批准工具调用的 mod， ask 规则会询问的调用，或我的 PreToolUse 连钩子拦截的调用也能代为批准。更进一步， 没有 managed settings，且未以 Team/Enterprise 套餐登录的个人用户的话，内置防护（sec-default@builtin ）根本不会加载，所以 deny 连规则已拦截的调用，mod 也能反转批准。不过 mod 无法更改 Claude Code 的 权限确认对话框本身无法更改。 无法操纵向用户显示什么。（官方文档： Extend permissions with hooks)

安装前自行确认

在直接从市场安装之前，可以不在运行的情况下查看该 mod 接收的事件和调用的 API。克隆仓库后在 shell 中执行。

claude plugin validate ./some-mod
  ❯ ./register.js hooks: session.start, tool.call, ui.render{component=Pane}
  ❯ ./register.js calls: $.fs.read, $.http.fetch, $.store.set, $.ui.open

calls: 行尤其值得关注的条目。

调用 含义
$.fs.read, $.fs.write 在我的账号能触达的任何位置读写文件
$.process.run, $.process.spawn 以我的权限执行程序
$.http.fetch 发送网络请求
$.env.get, $.settings.read 读取环境变量和配置。其中可能包含 API 密钥。输出的 env reads: 行会写出是哪个变量。
$.env.set 设置环境变量。可能影响此后 Claude Code 执行的所有命令和 MCP 服务器。 env writes: 行会写出是哪个变量。
$.mcp.call 在会话权限规则下调用已连接的 MCP 服务器的工具
$.model.complete 用我的套餐或 API 密钥调用模型
$.prompt.submit 代为发送提示词。也可以伪装成我输入的
$.session.send 发送会被其他会话或子代理中的 Claude 读取的消息

hooks: 行看重以下几点。 tool.call 和 prompt.submit ，意味着能查看并修改所有工具调用和提示词， session.append ，意味着能在对话的每一行被保存之前就改写它。 ui.render{component=AskUserQuestion} ，意味着可以重绘 Claude 向用户提问的对话框， tool.check，意味着能在权限确认框弹出之前就批准或拒绝工具调用。

官方文档： Review what a mod can do

k-mods 的审查方式

上架到 k-mods 目录的 mod，装之前会走这些流程。

  1. 许可证门槛：没有许可证的仓库代码，在拿到作者同意前不会收录。
  2. 提交固定（sha)：原样引入原版的 mod 会固定审查时点的确切提交。原仓库以后再怎么变，我拿到的都是审查过的那个代码。更新只在重新审查之后才上。
  3. 静态分析 + 代码阅读: claude plugin validate是否通过，并由人工通读全部代码（code-read）。mod 有测试的话也会看是否通过（unit-test），会画界面的 mod 会在真实会话里起一次确认（live-session）。每个 mod 页面的“审查方式”里写了走过哪些流程。
  4. 权限标签显示 ：根据静态分析找到的调用，给这个 mod 在我电脑上做的事打标签。下面 权限标签 参考。
  5. 更新时重新审查：升过版本的 mod 会重走第一次收录时的流程。
  6. 应作者要求删除：原作者要求下架就立刻从目录里撤掉。

官方文档： Plugin security and trust

权限标签

各 mod 页面会用标签标出静态分析找出的权限。按危险程度从高到低排列。

标签 含义
🌐 网络 $.http 或 $.mcp与互联网或外部服务器通信。对话内容可能外泄，请确认目的地
⚙️ 程序执行 $.process在我的电脑上执行程序
✏️ 文件写入 $.fs.write写入文件
🤖 模型调用 $.model调用模型。消耗我的用量
🛡️ 工具调用控制 tool.call 或 tool.check 可用钩子拦截工具调用或代为回答
💬 提示词输入 $.prompt.submit 或 $.prompt.fill代为填入或发送提示词
👀 对话读取 prompt.submit·turn.complete·session.append 钩子或绘制对话的界面， $.session.messages接触对话内容
🔑 环境与配置读取 $.env 或 $.settings读取
📂 文件读取 $.fs.read 系列的方式读取文件
📨 会话消息 $.session.send向其他会话发送消息
🔊 声音 $.audio发出声音
🎨 仅界面 以上都不做，只绘制界面

标签的读法。 绘制界面的 mod 几乎都带 👀（对话读取）。因为即使只接收回合结束的信号，Claude 的最后一条回答也会一并进来。所以不必仅凭 👀 一个就担心。真正要看的是 组合。即使有 👀，若没有 🌐（网络）、⚙️（程序执行）、💬（提示词输入），该 mod 就没有把对话送出设备之外的途径。💬 可能成为让 Claude 代为发送的绕行手段，所以要一并查看。反过来，若 👀 与 🌐 同时存在，请务必在 mod 页面的“代码中的地址”和审查笔记中确认向何处发送了什么。

一个 mod 可以带多个标签。若没有任何标签，表示这是一个只改界面的 mod。

k-mods 的 mod 页面怎么读

各 mod 页面（或 /plugin中查看的详细信息）中确认以下几项。

  • 种类（kind): 오리지널 （k-mods 从零制作）， 한국 수정판 （原版由 k-mods 修补）， 원본 （保持原样，只固定提交）， 묶음（把多个 mod 打包的安装组合）
  • 权限标签：上表里的标签
  • 审查记录：审查日期、审查用的 Claude Code 版本、审查方式（validate/code-read/unit-test/live-session），以及审查中发现的问题（网络目标、运行外部程序等）
  • 来源：原版 mod 就给原作者仓库和固定的提交链接。修改版就说明相对原版改了什么

若有疑点，安装前 claude plugin validate <복제한 폴더>自行再确认一次。

在公司或组织中使用时

如果是公司的 Claude Code 环境，管理员可以单独设置 mod 策略。

  • allowManagedModsOnly：开启后，用户安装的 mod 完全不会加载，只有组织分发的 mod 和 Claude Code 内置 mod 运行。k-mods 的 mod 在这项策略下也可能不加载。
  • prependPlugins/appendPlugins：设定组织策略 mod 比用户 mod 先（或后）执行的顺序。
  • sec-default@builtin ：有 managed settings，或用 Team、Enterprise 套餐登录时，先于所有用户安装的 mod 加载的内置防护。组织管理的系统提示、managed CLAUDE.md，保护 managed MCP 服务器的工具和说明不被用户 mod 碰到。除此之外不做别的拦截。

在公司环境里如果某个 k-mods mod 不显示，请先确认是否由这些策略导致。管理员侧的设置方法在官方文档里。

官方文档： Manage mods for your organization

请当心这类 mod

  • calls: 在行内 $.http.fetch 或 $.process.run，但说明的任何地方都没写为什么需要它。
  • hooks: 在行内 prompt.submit 或 session.append，但说明里没有写对话内容不会发送到设备之外。
  • tool.check这类可批准或拒绝工具调用的 mod，但源码未公开，或无法得知它接收哪个提交。
  • 来自完全没有许可证的仓库的代码。
  • 一边接收令牌或密码，一边 userConfig 的 sensitive 不做任何标记地以明文保存。
  • 说明写的是“只改界面”，却带着 🌐 网络或 ⚙️ 程序执行标签。说明与权限不符时，最好再多读一些代码。
